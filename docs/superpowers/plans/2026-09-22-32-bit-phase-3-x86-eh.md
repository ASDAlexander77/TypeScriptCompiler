# 32-bit Phase 3: Win32 x86 Exception Handling Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 32-bit Windows programs (`-mtriple=i686-pc-windows-msvc`) that throw and catch link and behave correctly under `-mm=gc`, `-mm=rc` and `-mm=none`.

**Architecture:** There are two narrow changes, both gated on `TargetInfo` policy predicates that Phase 1 introduced and nothing reads yet.
1. The EH cross-references in `ThrowInfo`, `CatchableType` and `CatchableTypeArray` are image-base-relative RVAs on x64 and absolute pointers on x86. The struct layouts are already identical, so only the stored value changes.
2. `_CxxThrowException` is `__stdcall` on x86. A small LLVM module pass sets that calling convention on the declaration and on every call site before optimization.

A third task links and runs the exception corpus as 32-bit binaries and fixes whatever that uncovers within scope.

**Tech Stack:** C++17, MLIR LLVM dialect, LLVM new pass manager, MSVC C++ EH (`__CxxFrameHandler3`), bash test scripts run by hand under Git Bash.

**Spec:** `docs/superpowers/specs/2026-09-20-32-bit-compilation-design.md`, section "Phase 3 — Win32 x86 exception handling", plus "Two findings that reduced scope".

- [ ] **Step 3: Implement in the LLVM-dialect helper.** Add one private method and use it at all three sites:

```cpp
    // A cross-reference inside ThrowInfo, CatchableType or CatchableTypeArray: an i32 field.
    // 64-bit MSVC stores an image-base-relative RVA there, 32-bit x86 the absolute address, which
    // is also 4 bytes - so the struct layouts coincide and only the value differs.
    mlir::Value ehReference(mlir::Location loc, mlir::Value ptrValue)
    {
        if (!compileOptions.targetInfo.usesImageBaseRelativeEH)
        {
            if (compileOptions.sizeBits() != 32)
            {
                llvm::report_fatal_error("absolute EH references need 32-bit pointers");
            }

            return rewriter.create<LLVM::PtrToIntOp>(loc, th.getI32Type(), ptrValue);
        }

        auto intPtrTy = rewriter.getIntegerType(compileOptions.sizeBits());
        auto ptrInt = rewriter.create<LLVM::PtrToIntOp>(loc, intPtrTy, ptrValue);
        auto imageBasePtr = rewriter.create<LLVM::AddressOfOp>(loc, th.getPtrType(),
                                                               FlatSymbolRefAttr::get(rewriter.getContext(), imageBaseRef));
        auto imageBaseInt = rewriter.create<LLVM::PtrToIntOp>(loc, intPtrTy, imageBasePtr);
        auto rva = rewriter.create<LLVM::SubOp>(loc, intPtrTy, ptrInt, imageBaseInt);
        return rewriter.create<LLVM::TruncOp>(loc, th.getI32Type(), rva);
    }
```

Each site becomes `auto itemValueN = ehReference(loc, <the AddressOfOp it already builds>);`. At x64 the result has exactly today's op sequence and types: `sizeBits()` is 64 there, which is the `i64` currently hard-coded. In `imageBase(loc)`, return `success()` without creating the global when `!usesImageBaseRelativeEH`. On x86 nothing references it, and an unused external `__ImageBase` would needlessly pull in `___ImageBase`. Check that this class has `compileOptions` and `th` members with these names. If the names differ, adapt them and say so in your report.

`_CxxThrowException` is declared in two places:

`Win32ExceptionPass` also rewrites calls into invokes (`ToInvoke`). So in LLVM IR, before optimization, the one place that sees every declaration and every call site is a module pass. The calling convention must be set on the callee **and** on every call site. A call whose calling convention differs from its callee's is undefined behaviour, and InstCombine replaces such calls with `unreachable`. That is why the pass must run before the optimization pipeline.

```cpp
#ifndef TYPESCRIPT_CXXTHROWCALLINGCONVPASS_H_
#define TYPESCRIPT_CXXTHROWCALLINGCONVPASS_H_

#include "llvm/IR/PassManager.h"

namespace ts
{
    // _CxxThrowException is __stdcall on 32-bit x86 MSVC; its symbol is then __CxxThrowException@8.
    // Sets that convention on the declaration and on every call and invoke of it. A call whose
    // convention differs from its callee's is undefined behaviour, which InstCombine turns into
    // `unreachable`, so this runs before the optimization pipeline.
    class CxxThrowCallingConvPass : public llvm::PassInfoMixin<CxxThrowCallingConvPass>
    {
      public:
        llvm::PreservedAnalyses run(llvm::Module &M, llvm::ModuleAnalysisManager &AM);
    };
} // namespace ts

#endif // TYPESCRIPT_CXXTHROWCALLINGCONVPASS_H_
```

`tslang/lib/TypeScriptExceptionPass/CxxThrowCallingConvPass.cpp`:

```cpp
#include "TypeScript/Pass/CxxThrowCallingConvPass.h"

#include "llvm/IR/InstrTypes.h"
#include "llvm/IR/Module.h"

namespace ts
{
    llvm::PreservedAnalyses CxxThrowCallingConvPass::run(llvm::Module &M, llvm::ModuleAnalysisManager &AM)
    {
        auto *throwFn = M.getFunction("_CxxThrowException");
        if (!throwFn)
        {
            return llvm::PreservedAnalyses::all();
        }

        throwFn->setCallingConv(llvm::CallingConv::X86_StdCall);
        for (auto *user : throwFn->users())
        {
            if (auto *call = llvm::dyn_cast<llvm::CallBase>(user))
            {
                if (call->getCalledOperand() == throwFn)
                {
                    call->setCallingConv(llvm::CallingConv::X86_StdCall);
                }
            }
        }

        return llvm::PreservedAnalyses::none();
    }
} // namespace ts
```

## Rulings made while writing this plan

- **The calling convention is set by one LLVM module pass**, not at each of the three places that create the declaration or a call. The MLIR lowering, the synthesized rethrow in `Win32ExceptionPass` and `ToInvoke` all create call sites. Only a module-level pass after all of them sees every one, and a single missed call site would be undefined behaviour that InstCombine turns into `unreachable`.
- **`__ImageBase` is not declared on x86.** Nothing references it there.
- **The helpers are not unified.** The LLVM-dialect and MLIR-level helpers each keep their own `ehReference`, because they build with different op sets. Merging them would be a refactor unrelated to 32-bit.
- **The corpus files are run directly by the x86 script, not through ctest.** Running the whole suite at 32 bits, through the test runner and with the default library, is Phase 4.
